# B13–B26 implementation walkthrough

This handoff supersedes B12's draw/winnings availability notes. It describes the final local implementation; [API](API.md) contains route/body contracts, [Deployment](Deployment.md) contains future configuration limits, and [Local readiness](Local-Readiness.md) records actual verification. No Git or deployment action accompanies these changes.

## Main data flow

1. A signed-in member enters scores. The score service rechecks entitlement and serializes the mutation, enforcing one round per date and five retained rounds. It also records eligibility history. Successful simulated billing similarly commits the payment allocation ledger, subscription and eligibility history atomically.
2. An administrator configures one monthly draft. An optional future cutoff starts a baseline history. When due, simulation gathers five eligible scores and active unsuspended membership at cutoff, successful monthly allocation snapshots and outstanding jackpot. The pure engine chooses distinct numbers and calculates integer prizes. Only the versioned preview is stored at this point.
3. Publication takes the exact reviewed preview ID. A transaction holds the same eligibility lock as member/admin changes, recalculates the source fingerprint and refuses stale review. It persists immutable results, winners, pending payouts and the new jackpot balance together. Concurrent same-version clicks return the same published result.
4. Member result pages read frozen snapshots, never current scores for historical comparisons. A winning member submits a PNG/JPEG. The server checks ownership, validates/re-encodes content and uploads privately. Only after storage succeeds does a revision-checked transaction attach the evidence. Failed persistence schedules/removes the staged asset.
5. Admin review appends approval/rejection history. Rejected members can resubmit without losing earlier evidence. Only approval permits a single manual/demo settlement with a unique reference. Subscriber totals read won and paid separately. Reports reconcile successful allocations, donations, awards, settlements and current rollover with documented time bases.
6. Every browser request uses credentials and mutation CSRF headers. Explicit read retries are safe; writes are never automatically repeated. Expired/suspended sessions clear private route state. Unexpected rendering failures show a focused safe recovery screen, and server exceptions expose only a safe code/message/request ID.

## Backend function contracts

Factories receive the dedicated Mongoose connection/models/config; no global production connection or import-time server startup is introduced. Route factories are called by `createRoutes`; services are called by those authenticated routes and deterministic tests. Model constructors return a registered/reused connection model; schema/index declarations do not themselves insert records.

## Frontend function/component contracts

Pages are called by AppRoutes; components receive server DTOs and callbacks. Their output is semantic React markup. Fetching uses abortable `useFetch`, and mutation callbacks refresh authoritative reads only after successful writes. ## Scripts, tests and file groups

- `backend/scripts/browser-server.js`: `startBrowserServer({seed})` creates an isolated local replica set, connects models, seeds fictional charities, optionally calls a fixture seeder, listens on loopback 4011 and returns idempotent teardown; startup failure cleans partial resources.
- `seed-operations-fixture.js`: `seedOperationsFixture(database,config)` refuses non-test mode, creates demo-only roles, a funded yearly member, five scores and a deterministic previous-month winning draw through the service. No route allows users to choose winning numbers. The fixture never runs in the normal server.
- `local-demo.js`: CLI uses the disposable harness, prints only localhost guidance, handles shutdown. It reads no private env. `indexes.js` loads the configured environment and creates declared indexes additively; never seed/drop. `cleanup-proof.js` invokes storage cleanup with safe failure reporting. These latter operator scripts are documented but were not run against user resources.
- `frontend/integration/setup.js`: starts isolated API and programmatic Vite with env loading disabled, fixed `/api` base and local proxy; owns teardown handles. Operations/run1 specs exercise real API journeys. `frontend/e2e/recovery.spec.js` injects statuses/offline and verifies focus/input/session recovery; existing foundation tests verify keyboard trap/restore/reduced motion and responsive navigation.
- Backend tests: draw.engine, draws-winners, admin, evidence, recovery-config plus existing auth/charity/payment/subscription/scores suites. Shared `test-support/fixture.js` creates private per-suite MongoDB, deterministic services and owned users, and returns teardown. It is not production data.
- Frontend tests: draw/winnings components, admin controls, crash/session recovery and API status/no-retry cases; existing auth/scores/subscription/home/common tests remain.
- Configuration/docs: backend/frontend package scripts, root lockfile dependencies (Cloudinary and sharp), `.env.example`, `render.yaml`, `frontend/vercel.json`, README, API, Decisions, Deployment, this handoff and Local-Readiness. Screenshots are generated local demo evidence, not live production totals.

No TODO, fake provider success, public proof URL or fabricated future draw date was added. Remaining external-service/PRD limitations are listed in Deployment and the readiness report.
